  ## Résultat : `@Transactional` sous Spring Boot 4 / Spring Framework 7
  
  Sources : doc de référence Spring Framework (déclaratif, rollback, résilience) via Context7 et WebFetch, et le source de `TransactionAutoConfiguration` au tag Spring Boot v4.0.0. Aucun fichier du dépôt n'a été lu ni modifié.
  
  **Annotation et package**
  - L'annotation est `@Transactional`, dans le package `org.springframework.transaction.annotation` (le package natif Spring, celui à utiliser).
  - `jakarta.transaction.Transactional` est aussi accepté. La doc le présente comme un « drop-in replacement », mais il n'expose pas les attributs Spring (`propagation` au sens Spring, `readOnly`, `timeout`, `label`…).
  
  **Attributs utiles** (table officielle)
  - `propagation` (enum `Propagation`, `REQUIRED` par défaut).
  - `isolation` (enum `Isolation`).
  - `readOnly`.
  - `timeout` en secondes, ou `timeoutString` pour un placeholder.
  - `rollbackFor` / `rollbackForClassName` et `noRollbackFor` / `noRollbackForClassName`.
  - `value` / `transactionManager` pour choisir le gestionnaire, et `label`.
  - `isolation`, `timeout` et `readOnly` ne s'appliquent qu'avec `REQUIRED` ou `REQUIRES_NEW`.
  
  **Ce qui est notable dans Boot 4 / Framework 7**
  - **Pas besoin d'`@EnableTransactionManagement` dans une app Boot.** Dans Boot 4.0.0, l'auto-configuration vit dans le module `spring-boot-transaction`, package `org.springframework.boot.transaction.autoconfigure`. Elle applique l'annotation elle-même dès qu'un bean `TransactionManager` existe.
  - **Les proxys sont CGLIB par défaut.** Pour avoir des proxys JDK, il faut `spring.aop.proxy-target-class=false`.
  - **Transactions réactives :** les méthodes qui renvoient `Mono`, `Flux` ou `Publisher` sont transactionnelles. Boot crée un bean `TransactionalOperator` s'il y a un seul `ReactiveTransactionManager`. Ce `ReactiveTransactionManager` n'est pas toujours auto-configuré : c'est le cas avec Neo4j réactif, où il faut le déclarer soi-même.
  - **Depuis 6.2**, on peut changer le rollback par défaut pour toute l'application : `@EnableTransactionManagement(rollbackOn = ALL_EXCEPTIONS)`. La doc le recommande, surtout en Kotlin.
  - **Nouveauté de 7.0 :** `@Retryable` et `@ConcurrencyLimit` font désormais partie du cœur du framework, à activer via `@EnableResilientMethods`.
  
  **Pièges courants**
  1. **Auto-invocation.** En mode proxy (le défaut), seul un appel venu de l'extérieur passe par le proxy. Un `this.autreMethode()` annotée n'ouvre donc aucune transaction. Les solutions sont le mode AspectJ ou un appel à un autre bean.
  2. **Visibilité des méthodes.** Depuis 6.0, les méthodes `protected` et package-private sont transactionnelles avec les proxys de classe (CGLIB). Avec les proxys d'interface, la méthode doit être `public` et déclarée dans l'interface. Les méthodes `private` ne le sont jamais en mode proxy.
  3. **Exceptions vérifiées.** Seules `RuntimeException` et `Error` déclenchent un rollback. Une checked exception laisse la transaction se committer, sauf avec `rollbackFor` ou `ALL_EXCEPTIONS`.
  4. **`@PostConstruct`.** Le proxy n'est pas encore complètement initialisé à ce moment-là, donc il ne faut pas compter sur la transaction.
  
  **Exemple**
  ```java
  import org.springframework.stereotype.Service;
  import org.springframework.transaction.annotation.Isolation;
  import org.springframework.transaction.annotation.Propagation;
  import org.springframework.transaction.annotation.Transactional;
  
  @Service
  @Transactional(readOnly = true)               // default for the class: read-only
  public class OrderService {
  
      private final OrderRepository orders;
  
      public OrderService(OrderRepository orders) { this.orders = orders; }
  
      public Order find(long id) {
          return orders.findById(id).orElseThrow();
      }
  
      @Transactional(
          propagation = Propagation.REQUIRED,
          isolation = Isolation.READ_COMMITTED,
          timeout = 10,
          rollbackFor = PaymentException.class) // checked exception: rollback too
      public Order place(Order o) throws PaymentException {
          Order saved = orders.save(o);
          charge(saved);                        // call through the proxy? no: self-invocation
          return saved;
      }
  
      void charge(Order o) throws PaymentException { /* ... */ }
  }
  ```
  
  ## Points ouverts
  - **Nouveautés transactionnelles de Framework 7.** La doc ne m'a montré aucun changement de `@Transactional` propre à 7.0 ; les notes vues portent sur 6.0 et 6.2. Je n'ai pas lu les release notes de 7.0, donc je ne peux pas affirmer qu'il n'y en a aucun.
  - **`@Retryable` combiné à `@Transactional`.** Je n'ai pas vérifié l'ordre des deux intercepteurs. Pour qu'une nouvelle tentative rouvre une transaction, il faut que le retry enveloppe la transaction ; ce n'est pas confirmé.
  - **Propriétés `spring.transaction.*` de Boot 4** (par exemple le timeout par défaut) : non vérifiées.
  - **Kotlin `suspend`.** Le support des coroutines n'est pas cité sur la page consultée : seul l'exemple `Flow` y figure.
