  Ce que fait Go (vérifié dans le source de Go 1.27, `vendor/golang.org/x/net/http/httpproxy/proxy.go:92-95, 170-200`) :

  - **NO_PROXY :** accepte une liste séparée par des virgules, des noms, des suffixes (`.example.com` ou `example.com`, qui couvre aussi les sous-domaines), `*`, des IP, des CIDR et `hôte:port`. Un CIDR ne s'applique qu'à une IP littérale dans l'URL, jamais à un nom résolu.

  ### Garde anti-SSRF de `internal/oci` et NO_PROXY (D156)
  
  - **Fonctionnement :** `dialControl` (`internal/oci/oci_blob.go:75-90`) refuse à la connexion une adresse de bouclage, link-local ou non spécifiée. Seule exception : l'ip:port d'un proxy que la fonction `Proxy` a choisi pour une requête. `proxyAddrs.add` le résout une fois et le garde (`oci_blob.go:122-147`, port par défaut selon le schéma : 80, 443, 1080 pour socks5 et socks5h). Un proxy local comme cntlm sur 127.0.0.1 continue donc de marcher.
  - **Une cible exclue par NO_PROXY :** `Proxy()` renvoie nil et ne déclare rien. La connexion est directe et la garde s'applique sur l'IP résolue.
  - **Risque résiduel accepté (4) de D156 :** une fois un proxy vu, son ip:port reste autorisé pour toute connexion du transport. Un nom exclu par NO_PROXY qui résout vers cet ip:port passe donc en direct (GET anonyme).
  - **Risque résiduel (3) :** derrière un proxy, c'est le proxy qui résout la cible, donc seule la vérification du nom littéral (`followBlobRedirect`) protège.
  - **Seul composant testé avec un proxy :** `internal/oci/oci_blob_proxy_test.go`, avec un proxy injecté par `newBlobTransport` puisque `ProxyFromEnvironment` est figé par processus.
  
  ### Incohérences et trous
  
  1. **Les Diagnostics contournent le proxy sans le dire.** Le HEAD HTTP a un Transport explicite sans `Proxy` (`internal/netcheck/env.go:306`). Le stage HTTP dépend en plus du stage connect, qui est une connexion TCP directe (`internal/netcheck/stage_http.go:22-30`). Derrière un proxy obligatoire, l'écran conclut « injoignable » alors que tous les autres clients de DevDesk passent par le proxy. Aucune ligne n'indique qu'un proxy est configuré pour cette cible ni que NO_PROXY l'exclut. Un diagnostic direct peut être voulu, mais rien dans le code ni dans la doc ne le dit.
  2. **Les moniteurs de statut divergent.** Un moniteur `http`/`https` passe par le proxy, un moniteur `ssl` sur la même cible part en direct (`internal/status/tls_dial.go:27`). L'un peut être vert et l'autre en erreur pour le même hôte.
  3. **Les scanners en conteneur ne reçoivent pas l'environnement.** C'est le cas de Trivy, qui télécharge sa base, et de cosign, qui interroge le registre. Ce qui suit vient du fonctionnement des moteurs, pas du code de DevDesk :
     - la CLI Docker injecte les proxys de `~/.docker/config.json` (`proxies`), pas ceux de l'environnement ;
     - podman transmet par défaut les variables de l'hôte (`--http-proxy=true`) ;
     - dans les deux cas, un proxy sur 127.0.0.1 n'est pas joignable depuis un conteneur en réseau bridge.
  
     DevDesk donne donc un résultat différent selon le moteur et la source de l'outil (binaire ou conteneur).
  4. **La sémantique change entre Go et git.** libcurl ignore `HTTP_PROXY` en majuscules pour les URL `http://` (protection httpoxy) et lit `all_proxy`. Go lit `HTTP_PROXY` mais pas `ALL_PROXY`. Avec seulement `HTTP_PROXY=…` posé, l'API GitLab sur `http://` passe par le proxy mais pas le clone. Avec seulement `ALL_PROXY=socks5://…`, c'est l'inverse : le clone passe par le proxy, aucun client Go. C'est le comportement de libcurl, pas du code DevDesk.
  5. **Les noms `*.localhost` partent au proxy.** Go n'exempte que `localhost` exact. Un registre `foo.localhost:5000`, que `internal/oci` traite comme local (`isLocalURL`), est envoyé au proxy sauf si NO_PROXY le couvre.
  6. **Les pulls ne passent pas par l'environnement de DevDesk.** Avec Docker, c'est le démon qui tire, selon sa propre config proxy (non vérifiable dans le code).
  7. **Rien n'est documenté ni montré à l'utilisateur.** Aucune doc ne dit que DevDesk suit HTTP(S)_PROXY et NO_PROXY, que ALL_PROXY n'est pas lue, ni que les variables sont lues une fois au démarrage. Aucun écran n'indique le proxy actif. Il n'y a pas de test de contrat du type « chaque client de production garde `ProxyFromEnvironment` » : un futur `&http.Transport{…}` sans `Proxy`, comme celui de `netcheck`, passerait sans alerte.
