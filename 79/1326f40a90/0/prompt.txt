  ### New constats
  
  **N1 — High, verified, the same class as (3): migration into a git helper that does not persist.** internal/credentials/select.go:243-256 (`usableHelperName`) and internal/credentials/migrate.go:84-87.

  - Proven with a temp repo whose `.git/config` adds `credential.helper = !f() { cat > leak; }; f`. With `auto` plus a silent keyring, and with git pinned, Select picks git (Detail "…helper (f())"). `Save` hands the token to that shell command and the leak file contains it.
  - The same helper also runs on `fill`, so on every `Load` at startup. That is arbitrary code execution as soon as DevDesk starts in such a directory, with no token involved.
  - Exposure: DevDesk is launched from the user's shell, often inside a project, and has no `os.Chdir`. The attacker needs control of `.git/config`: a zip or tar archive that includes `.git/`, or a repo the user owns that a third-party tool modified. A plain `git clone` does not copy `.git/config`. A directory owned by another user is blocked by `safe.directory` (git ≥ 2.35.2).
  - How the branch widens it: before, a silent keyring hung DevDesk forever, so git was never reached. Now `auto` falls back to git in exactly that case.
  - Fix: run both commands from a neutral directory that is not a repo, with `GIT_CEILING_DIRECTORIES` set. For example `cmd.Dir` = a fresh temp dir, or set `GIT_DIR` to an empty dir.   **N4 — Low, suspicion, not proven.** internal/credentials/git_credential.go:133 puts git's stderr into the error, which ends up in notes and logs. A helper that echoes its input on stderr would expose the secret. This predates the branch. Fix: do not include stderr, or redact it.

The test that triggered it would not fail. The runtime guard is therefore blind to a store that blocks and then panics.
