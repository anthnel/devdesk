## 1. Model structure — `internal/ui/workspaces/model.go`

`Model` (lines 30-114) is **not** a general expand/collapse tree model. It is a **drill-down, single-level-at-a-time file browser**, closer to a classic file explorer than a tree view:

**Critical architectural fact: there is no in-memory representation of the whole workspace tree.** `loadEntries()` (`entries.go`... actually `table.go:60-126`) reads exactly one directory (`os.ReadDir`) per navigation step and replaces the table's rows. The closest thing to a recursive tree walk is `detectSubRepos`/`walkSubRepos` in `entry.go:112-195`, but that only discovers **git repository locations** nested under a directory (for S/F/A targeting), not a full listing of every file/dir path, and it does not build any row/UI representation — it returns `[]string` repo paths only.

## 2. Tree representation / rows

There is no "tree flattened into indented rows" — the table is always just the current directory's children, no indentation, no depth column. Row type: `workspaceRow` (`columns.go:35-48`):

```go
type workspaceRow struct {
    Entry Entry
    GitStatus string
    Sensitive secretsCell
    CI ciCell
    Critical, High, Medium, Low string
    Scanned string
}
```

`Entry` (`model.go:117-138`) is one filesystem entry: `Name`, `Path`, `ModTime`, `IsDir`, plus git metadata (`IsGitRepo`, `GitBranch`, etc.) and `SubRepoPaths`/`SubRepoSkipped` for aggregation when the entry is a non-git directory.

**There is no existing function that "expands the tree to a specific path and selects it."** Navigation only ever moves one level at a time via `navigateIn()`/`navigateUp()` (`update.go:319-366`), each triggering a fresh `loadEntries()` Cmd. To land on an arbitrary nested path, a new feature would need to synthesize the intermediate `navigationStack`/`cursorStack` state and either (a) issue a chain of loads level-by-level, or (b) directly build `currentPath` = the parent of the target, `navigationStack` = all its ancestors, then load and set `pendingCursor` to the matching row once `EntriesLoadedMsg` lands. Nothing like this exists today — it would be new code.

`rowsFor(entries []Entry)` (`table.go`/`columns.go:167-197`) decorates entries into rows (adds scan/spinner state); `setEntries` (`table.go:23-26`) calls `m.table.SetItems` + `Remeasure()`; `refreshRows` (`table.go:36-38`) rebuilds rows without remeasuring (used for spinner ticks).

### Summary of what a fuzzy-find "G-mode" would have to reconcile with existing architecture (facts only, no proposal)

2. **A full-tree fuzzy search needs its own recursive filesystem walk** (something like `walkSubRepos` in shape, but collecting all paths, not just repo roots) — nothing today builds that list.
3. **`G` is already claimed** by the app-wide uppercase vocabulary (`keymap.Get`, "Pull (get) the image or tag") per Rule 111; declared-free uppercase letters are only `J`, `Q`, `Z`. Lowercase `g` is also not declared as a workspaces local toggle in `keymap.localToggles`.
4. **The mode-switch shape to follow** is the existing `ViewMode` enum + `mode`/component-pointer field pattern (`ModeAdding`/`WorkspaceInput` is the closest precedent for "a component that owns its own key handling while a mode flag is set"), dispatched with top priority in `handleKeyMsg`, mirrored in `View()`, `GetShortcuts()`, and `GetFooterHeight()`/`RenderFooter()`.
5. **Existing `/` FilterBar is a *different* feature** (single-directory substring filter, not a cross-tree fuzzy finder) but is the closest UI/interaction precedent in this package for "type into a bar, get a live-updating list."
6. **Rule 112 tension**: workspaces' own `ModeAdding`/`ModeRenaming` already render as centered overlays rather than full-viewport forms, which is worth being aware of as precedent (or as a deviation) when deciding how the new search UI should be laid out.</result>
