## Epic : Kyverno — politiques sur manifestes

(L'epic ne dit plus « d'organisation » pour le spike : le jeu standard a été mesuré et écarté ; les politiques d'organisation sont la piste restante, voir S7. Le titre Plane de DEVDESK-10 est recadré sur les politiques propres de l'organisation.)

### S0 — Mesurer `kyverno apply` avec le jeu standard `restricted` de Kyverno, et ce qu'il apporte en plus de Trivy, avant d'investir (spike)
Epic : Kyverno — politiques sur manifestes — Priorité : Must — Effort : M (hypothèse : un binaire `kyverno` installable sans accès au cluster ; un jeu d'environ 19 politiques ; 2 à 3 dépôts de test)

**Résultat (2026-11-22) : terminé, verdict NO-GO** (O = 97,7 % pour un seuil de no-go à 85 % ; détail et valeurs par seuil dans la note [`docs/measurements/2026-11-22-kyverno-apply.md`](../../measurements/2026-11-22-kyverno-apply.md)). Le texte ci-dessous (critères, seuils, grille, questions) est conservé tel qu'il a été validé avant le run ; il n'est pas modifié après coup.

Time-box proposé : **une demi-journée (environ 4 h de travail), à compter de la réception des entrées listées plus bas** ; plafond dur d'une journée. À l'échéance, tout critère non couvert est écrit « non mesuré » dans la note et la décision se prend sur ce qui est mesuré (une décision « non tranchable, voici ce qui manque » est un résultat valable).

En tant que product owner de DevDesk, je veux une note de mesure datée qui dit si le jeu `restricted` standard de Kyverno, appliqué avec `kyverno apply` à des manifestes, trouve des violations que Trivy ne trouve pas déjà, et si l'outil est assez fiable hors cluster pour être intégré, afin de décider, chiffres à l'appui, entre construire l'étage Kyverno (go), l'abandonner (no-go) ou le remplacer par des contrôles Rego dans Trivy (pivot), sans avoir écrit une ligne de code de production.

**Ce que le spike mesure, en une phrase** : le recouvrement avec Trivy est LE critère de valeur. Le profil `restricted` recoupe fortement les contrôles `KSV-*` de Trivy ; **un no-go parce que Trivy voit déjà l'essentiel est un résultat acceptable pour ce spike**, pas un échec.

**Livrable** : `docs/measurements/<date-du-run>-kyverno-apply.md`, au format des notes voisines (par exemple `docs/measurements/2026-11-21-docker-hub-anonymous.md`) : en-tête (sujet, méthode, isolation, machine, versions), une section par critère avec le verdict, les écarts, puis les questions bloquantes. Règle du dossier, reprise telle quelle : **un chiffre vient d'une mesure (commande + sortie citées), sinon il est écrit « non mesuré »** ; aucune valeur de `research.md` ni du constat web de ce brief n'est recopiée sans être remesurée ; une note datée n'est jamais corrigée après coup, un nouveau run donne une nouvelle note. Aucun fichier de production n'est modifié ; les scripts du run vivent hors du dépôt ou sont jetés, rien n'est commité hormis la note. Le jeu de politiques étant public, ses noms, extraits et résultats peuvent figurer dans la note (plus d'anonymisation des politiques).

**Le jeu de politiques mesuré** (constat web du 2026-11-22, non remesuré ; la note le recompte sur le clone)
- Dépôt `kyverno/policies` ; sur la branche `main`, le dossier est **`pod-security-vpol/`**, avec les sous-dossiers `baseline/` et `restricted/` et un `EXCEPTIONS.md`. L'ancien chemin `pod-security/restricted` (et `pod-security/`) renvoie une erreur 404 sur `main`.
- `pod-security-vpol/restricted/` : 7 politiques d'après la liste du dossier et de son `kustomization.yaml` (`disallow-capabilities-strict`, `disallow-privilege-escalation`, `disallow-proc-mount-strict`, `require-run-as-non-root-user`, `require-run-as-nonroot`, `restrict-seccomp-strict`, `restrict-volume-types`).
- `pod-security-vpol/baseline/` : 12 politiques d'après le `kustomization.yaml` (capabilities, host namespaces, hostPath, host ports, host probes, host process, privileged, proc mount, SELinux, AppArmor, seccomp, sysctls) ; **nombre exact à vérifier**.
- Le profil `restricted` des PSS est cumulatif (il inclut `baseline`) : le jeu à appliquer est donc `baseline/` + `restricted/`, soit **19 politiques (à vérifier)**. Le guide de Kyverno ne dit pas explicitement que `restricted` inclut `baseline` côté dépôt ; l'utilisateur confirme (question 3).
- Variante CEL / variante héritée : le dépôt `main` ne livre que du **CEL en `policies.kyverno.io/v1`** (ici `kind: ValidatingPolicy`, `validationActions: [Audit]`, annotation `policies.kyverno.io/severity`, `policies.kyverno.io/minversion: 1.19.1` sur la politique lue). Son README dit que les exemples `ClusterPolicy`, `Policy`, `ClusterCleanupPolicy` et `CleanupPolicy` y ont été **retirés**. La documentation de Kyverno et le site `kyverno.io/policies` mentionnent encore un chemin `pod-security` en `ClusterPolicy` et un `pod-security-cel` : il n'est pas établi quel ref du dépôt porte encore la variante héritée (le dépôt n'affiche aucune release) ; **à vérifier sur le clone**, avec `git log`/`git ls-tree` sur le ref utilisé.
- Conséquence : la contradiction de Kyverno 1.20 sur les `ClusterPolicy` (rejet ou simple avertissement) ne touche plus l'utilisateur tant qu'il applique le jeu de `main` ; elle reste **centrale** pour la compatibilité de version : (a) le jeu `main` est-il chargé par le CLI de la version retenue (la politique lue annonce `minversion: 1.19.1`) ; (b) un cluster plus ancien oblige-t-il à prendre la variante `ClusterPolicy` d'un ref plus ancien, et le CLI 1.20 la charge-t-il ?
- Les politiques lues utilisent une variable CEL `exceptions.allowedImages` (mécanisme d'exceptions de Kyverno) : le CLI hors cluster doit l'évaluer sans `PolicyException` ; **à mesurer**.

**Critères d'acceptation** (chacun est une section de la note, avec un verdict « OK / écart / non mesuré »)

1. **Version et provenance.** Étant donné un binaire `kyverno` installé (ou l'image `ghcr.io/kyverno/kyverno-cli`) et le clone du dépôt `kyverno/policies` fait par l'utilisateur, quand on lance `kyverno version` et `git -C <clone> rev-parse HEAD`, alors la note cite la sortie exacte (version, commit si affiché), le ref et le SHA du clone, la version de Kyverno du cluster de l'utilisateur (si elle existe) et dit si elle est alignée avec celle du CLI ; si elle ne l'est pas, le critère 2 est rejoué avec la version du cluster (tag d'image épinglé ou binaire de cette version) et les deux résultats figurent dans la note. Elle recompte aussi sur le clone, fichier par fichier, les politiques de `baseline/` et `restricted/` (nom, `kind`, `apiVersion`, valeur de `policies.kyverno.io/severity`) et dit si le nom du dossier et les nombres (7, 12, 19) du brief se vérifient ; sinon l'écart est écrit.
2. **Chargement et types de politique.** Étant donné les politiques de `baseline/` et `restricted/`, quand on lance `kyverno apply <répertoire> -r <manifestes>` avec la version du critère 1, alors la note donne par type de politique le nombre de politiques, chargées, rejetées, le texte exact de l'erreur et le code de sortie pour chaque rejet. Elle tranche la contradiction de `research.md` sur les `ClusterPolicy` (rejet avec erreur ou simple avertissement de dépréciation) **par une sortie réelle** : si l'utilisateur fournit (hors time-box) un clone d'un ref portant la variante `ClusterPolicy` du même jeu, elle l'applique avec la version 1.20.x et donne les mêmes chiffres ; sinon la ligne est « non mesuré : aucune variante héritée fournie » et le constat « le jeu standard est livré en `policies.kyverno.io` » est la réponse. Elle dit enfin si un répertoire mêlant politiques acceptées et rejetées échoue entièrement ou en partie.
3. **Format du rapport.** Étant donné `kyverno apply ... -p --output-format json` (ou l'équivalent de la version) lancé sur des manifestes qui donnent au moins un `fail` et un `pass` pour le jeu, plus une politique de test sans annotation de gravité, une avec chacune des valeurs `low`, `medium`, `high`, `critical`, et une en `scored: "false"` (les 19 politiques du jeu ne couvrent peut-être pas toutes ces valeurs : la note donne d'abord la répartition réelle des gravités du jeu), quand on lit la sortie, alors la note contient un exemple brut (coupé) et un tableau des chemins JSON réels : où se trouvent politique, règle, résultat (`pass/fail/warn/skip/error`), gravité, message, ressource (kind, nom, namespace). Elle dit si la sortie est un seul document JSON ou plusieurs (séparés comment), si la gravité est reprise de l'annotation, absente ou vide quand l'annotation manque, ce que devient `critical`, et si `Audit` ou `Enforce` (`validationActions`) change quoi que ce soit au résultat. Elle indique si toutes les politiques du jeu ont la même gravité (auquel cas la règle « gravité de la politique » ne différencie rien).
4. **Fiabilité hors cluster.** Étant donné chacune des 19 politiques et, pour chacune, un manifeste minimal conforme et un manifeste minimal non conforme (réutiliser les cas de test du dépôt s'ils existent : **à vérifier**, le fichier `EXCEPTIONS.md` mentionne des suites `.kyverno-test-exceptions/`), quand on les applique sans cluster ni réseau, alors la note donne pour chaque politique le verdict obtenu (pass / fail / skip / error / aucun résultat) sur les deux manifestes, la raison pour skip et error, et le nombre de verdicts justes sur 19 × 2. Elle vérifie que les ressources `Pod`, `Deployment`, `StatefulSet`, `DaemonSet`, `Job` et `CronJob` produisent un verdict (les politiques lues listent ces types dans `matchConstraints` ; l'autogen n'est donc probablement pas en jeu : à confirmer), que la variable `exceptions.*` n'empêche pas l'évaluation, et compte à part les politiques qui utilisent `apiCall`, `configMap`, `request.*` ou `namespaceSelector` (recherche textuelle) comparées à celles classées skip/error. Elle dit si le run a tenté un accès réseau (run sans réseau ou capture des connexions ; la méthode est citée).
5. **Rattachement à un fichier et une ligne.** Étant donné 2 à 3 dépôts de test (voir « Dépôts de test »), couvrant au moins : manifestes bruts, Kustomize base + overlays, chart Helm rendu par `helm template`, quand on applique le jeu et qu'on rapproche chaque `fail` de la source, alors la note donne, par dépôt et par mode, le nombre total de violations et le nombre **rattachables sans ambiguïté** à un fichier et une ligne (définition de la note : exactement un document source correspond à kind + namespace + nom, et on connaît la ligne de son `metadata.name` ou de sa clef `kind`), le nombre ambigu (plusieurs correspondances : même objet dans plusieurs overlays ou dossiers, namespace posé par l'overlay, nom généré, ressource issue d'un rendu Helm sans fichier source) et le nombre introuvable, avec un exemple de chaque cas ; pour Helm et Kustomize, elle sépare « rattachable au fichier source ou au chart » de « rattachable à la ligne ».
6. **Recouvrement avec Trivy (critère de valeur).** Étant donné **les mêmes manifestes et les mêmes ressources** que ceux du critère 4 et 5 et la version de Trivy citée dans la note (`trivy --version`, base de checks à jour, `trivy config` avec ses réglages par défaut, **tous niveaux de gravité**, sans filtre qui biaise le résultat), quand on rapproche chaque violation Kyverno d'un finding `KSV-*` / `AVD-KSV-*` sur la même ressource portant sur la même condition, alors la note procède en deux temps :
   - **Avant d'ouvrir les chiffres du run**, une table de correspondance par politique (les 19 politiques du jeu contre les `KSV-*` de Trivy qui visent le même contrôle, ou « aucun check Trivy ») est écrite à partir de la lecture des politiques et des checks ; elle est citée telle quelle dans la note. Elle donne le nombre de politiques **sans aucun check Trivy** et celui de politiques avec au moins un check.
   - **Instance par instance** : l'unité de comptage est le couple (ressource, politique Kyverno) en échec ; plusieurs findings Trivy sur plusieurs conteneurs d'une même ressource ne comptent que pour un couple. Pour chaque couple, la note dit « couvert par Trivy » (paire citée, avec l'identifiant `KSV-*`) ou « résiduel » (jugement humain ; les cas douteux sont listés à part et comptés comme couverts). Elle donne : le **taux de recouvrement O** (couples couverts / couples en échec) pour l'ensemble et par dépôt, le nombre de politiques distinctes concernées, et la liste des politiques à violations résiduelles.
7. **Valeur résiduelle.** Étant donné les violations résiduelles du critère 6, quand on lit chacune dans sa source (échantillon de 10 au plus, tirées au sort, toutes si moins de 10), alors la note dit pour chacune si c'est une vraie non-conformité au profil `restricted` des PSS (vrai positif) ou un artefact (faux positif : politique trop large, variable `exceptions`, gabarit Helm, ressource qui n'est pas une charge de travail), et donne : le nombre de violations résiduelles, le nombre de ressources et de politiques distinctes touchées, la **précision** de l'échantillon (vrais positifs / vérifiés) et, pour chaque contrôle résiduel, une phrase sur ce qu'il demanderait à Trivy pour le couvrir (contrôle Rego ou autre ; sans estimer le coût de réécriture).
8. **Erreurs et cas limites.** Étant donné des entrées volontairement dégradées, quand on lance la commande, alors la note donne pour chaque cas le code de sortie, les premières lignes de stdout et de stderr, et dit si DevDesk pourrait distinguer ce cas d'un run propre : (a) politique en YAML mal formé, (b) politique en YAML valide mais invalide pour Kyverno (par exemple une expression CEL fausse), (c) répertoire de politiques vide, (d) répertoire de politiques inexistant, (e) répertoire de manifestes vide ou sans ressource Kubernetes, (f) manifeste mal formé, (g) violations présentes, (h) aucune violation. La note vérifie aussi si le code de sortie est cohérent avec le rapport quand il y a des violations (un code 0 avec violations est signalé dans `research.md` pour la 1.12.5) et note quel signal est fiable : le code, le rapport, ou les deux.
9. **Décision chiffrée.** Étant donné les sections 1 à 8 remplies, quand on applique la grille de décision ci-dessous, alors la note se termine par un seul verdict, **go**, **no-go** ou **pivot (Trivy + contrôles Rego)**, avec pour chaque seuil la valeur mesurée, le seuil retenu et « atteint / non atteint / non mesuré » ; un seuil non mesuré ne compte jamais comme atteint. Si le verdict est no-go sur le recouvrement, la note liste malgré tout les contrôles résiduels (critère 7), pour mémoire. L'utilisateur valide ou modifie les seuils avant le run : ils ne sont pas ajustés après avoir vu les chiffres.

## Stories d'implémentation du jeu standard (S1 à S6) : non retenues après le no-go

- **S1 — Jalon 1, manifestes bruts** (non retenue après le no-go) : un étage Kyverno optionnel (activé par `scan.kyverno_policies`, que l'utilisateur renseigne avec le répertoire qu'il a lui-même cloné ; mode d'exécution `auto | binary | image`) applique ce répertoire aux manifestes que `k8s.Discover` trouve et affiche les violations en Misconfiguration, source `kyverno`, avec fichier et ligne. ## S7 — Politiques propres à l'organisation (seule piste restante, DEVDESK-10, Backlog, non cadrée)

Décision de l'utilisateur du 2026-11-22, après le no-go de S0 : DEVDESK-10 reste en Backlog, **recadré sur les politiques propres de l'organisation** ; le jeu standard `restricted` est couvert par Trivy et n'est plus l'objet.

**Idée** : appliquer le jeu de politiques Kyverno d'une organisation (le sien, pas celui de `kyverno/policies`) aux manifestes d'un dépôt, pour faire respecter des règles que Trivy et kubeconform ne connaissent pas. C'est la valeur initiale de §3.85 : `kyverno apply` n'embarque aucune politique, sa valeur est d'appliquer celles de l'utilisateur.

**Ce que S0 a établi et qui vaut pour S7** (mesuré sur le jeu standard, Kyverno 1.19.2, Trivy 0.76.2, 4 dépôts publics ; à refaire ou à confirmer sur le jeu réel) :
- Le moteur tient hors cluster : 38/38 verdicts justes sur les 19 politiques, 228/228 sur six types de charge, aucun accès réseau nécessaire pour ce jeu. Cela ne dit rien d'un jeu d'organisation qui utiliserait `apiCall`, `configMap` ou `request.*`.
- Le rapport n'a ni fichier, ni ligne, ni champ `rule` : le rattachement se fait par kind + namespace + nom (73,1 % sans ambiguïté avec un run par dépôt, 98,9 % avec un run par fichier ; 45,3 % en rendu Helm/Kustomize).
- **Risque : faux verts silencieux.** Une politique au YAML mal formé, un répertoire de politiques vide ou inexistant, ou un fichier qui n'est pas une politique donnent un code de sortie 0 (ou 1 pour une autre raison), rien sur stderr et un rapport vide ou incomplet : DevDesk ne peut pas les distinguer d'un run propre sans contrôle de son côté. Un jeu d'organisation avec une politique cassée serait donc silencieusement non appliqué.
- Autres constats utiles : un doublon (même kind, namespace, nom) fait paniquer `kyverno apply` (code 2) ; un YAML sans `kind` ou un manifeste mal formé fait échouer tout le run ; `-r` n'est pas récursif ; les `ClusterPolicy` héritées chargent sur 1.19.2 avec un avertissement sur stdout avant le JSON (le flux n'est plus un JSON valide) ; une gravité inconnue est ignorée sans message.

**Prérequis avant toute story d'implémentation** (rien n'est lancé tant qu'ils ne sont pas remplis) :
1. **Avoir un jeu réel** : l'utilisateur fournit le jeu de politiques de l'organisation (ou un échantillon représentatif). Sans lui, S7 reste non cadrée. Les anciens critères d'anonymisation des politiques reviennent avec lui (un jeu d'organisation n'est cité dans une note que sous un nom générique, sauf accord).
2. **Mesurer le recouvrement avec Trivy sur CES politiques** : même méthode que le critère 6 de S0 (table de correspondance écrite avant les chiffres, comptage par couple ressource + politique, valeur résiduelle vérifiée à la main). Le 97,7 % du jeu standard ne se transpose pas : l'intérêt de S7 vient précisément de règles que Trivy n'a pas. Si le recouvrement est élevé, S7 perd sa raison d'être ; c'est à l'utilisateur de trancher.
3. **Connaître la version de Kyverno du cluster** (non mesurée par S0) et mesurer avec elle, et avec la 1.20.x si elle est publiée (non mesurée par S0 : comportement des `ClusterPolicy` sous 1.20, rejet ou avertissement). Si le jeu est en `ClusterPolicy`, c'est central.
4. **Traiter les faux verts silencieux comme un risque de conception, pas un détail** : toute story d'implémentation devra prévoir un contrôle côté DevDesk (le répertoire existe et contient au moins une politique valide, le nombre de politiques évaluées dans le rapport est celui attendu) avant d'afficher « aucune violation ». Le seuil T6 de S0 (aucun faux vert silencieux sans contournement) est à rejouer.
5. **Vérifier que le besoin existe** : le jeu d'organisation n'est pas déjà appliqué en CI ou à l'admission (ancienne hypothèse A du brief, retirée pour le jeu standard, qui revient ici).

**Forme possible, si les prérequis sont remplis** (non engagée) : reprendre les pistes S1 à S6 ci-dessus, réécrites pour ce jeu (étage optionnel activé par `scan.kyverno_policies`, run par fichier pour le rattachement, contrôle des faux verts, gravité). Un spike de mesure ou une extension de S0 précède, avec ses seuils validés avant le run.
