contradictoires relevés au point 8 n'est corrigé ici.

Convention de lecture : **Fait mesuré** = observé, la sortie est reproduite. **Non mesuré** = dit comme tel.

Les mesures de Podman : sur la VM, le texte de santé ne change **pas tout seul** dans les 20 s (voir 1) : le résultat de la

## 1. `ps` : état et libellé de statut avec santé

Conteneur créé par
`$E run -d --name ddm-health --health-cmd 'test -f /tmp/ok' --health-interval 2s --health-timeout 2s --health-retries 1 alpine:3.20 sleep 600`,
lu par `$E ps --filter name=ddm-health --format '{{.State}}|{{.Status}}'` (et `$E ps -a ...` une fois arrêté).

| Étape | Docker 29.10.1 et 28.5.2 | Podman 6.2.1 et 5.8.11 (rootful et rootless) |
|---|---|---|
| juste après `run` | `running\|Up 1 second (health: starting)` | `running\|Up Less than a second (starting)` (ou `Up 1 second (starting)`) |
| sonde en échec (`/tmp/ok` absent) | `running\|Up 5 seconds (unhealthy)` | `unhealthy` seulement après `podman healthcheck run` (exit 1, stdout `unhealthy`) : `running\|Up 1 second (unhealthy)` |
| après `touch /tmp/ok` | `running\|Up 10 seconds (healthy)` | après `podman healthcheck run` (exit 0, sans sortie) : `running\|Up 2 seconds (healthy)` |
| après `rm /tmp/ok` | `running\|Up 16 seconds (unhealthy)` | après `podman healthcheck run` (exit 1) : `running\|Up 2 seconds (unhealthy)` |
| arrêté (`$E stop -t 1`) | `exited\|Exited (137) Less than a second ago` | `exited\|Exited (137) 1 second ago (starting)` : **le suffixe de santé reste après l'arrêt** |

Faits :

- Docker écrit `(health: starting)` pour le démarrage, mais `(healthy)` et `(unhealthy)` sans le préfixe `health:`.
  Podman écrit `(starting)`, `(healthy)`, `(unhealthy)`.
- Sous Podman, `{{.State}}` reste `running` dans tous les cas : la santé n'existe que dans `{{.Status}}`.
- Table par défaut (`$E ps`, sans `--format`) : Docker affiche l'image `alpine:3.20` et `"sleep 600"` entre guillemets ; Podman
  affiche `docker.io/library/alpine:3.20` et `sleep 600` sans guillemets, des colonnes séparées par deux espaces.
- **Sur cette VM, Podman n'a pas fait passer la santé de `starting` à `healthy` ou `unhealthy` de lui-même en 20 s**
  (`podman inspect --format '{{json .State.Health}}'` : `{"Status":"starting","FailingStreak":0,"Log":null}` après 8 s avec
  `--health-interval 2s`), alors que Docker l'a fait en 5 s. Aucune minuterie systemd de Podman n'était listée
  (`systemctl list-timers`). Cause non établie : le build est le `podman-static` tiers, sans paquet systemd ; à ne pas
  généraliser à un Podman installé par la distribution (non mesuré). Conséquence pour les fixtures : l'enregistrement de
  `unhealthy` sous Podman exige d'appeler `podman healthcheck run`.

## 2. Refus sur ressource utilisée, sortie et code de sortie

Préparation : `$E network create ddm-net`, `$E volume create ddm-vol`,
`$E run -d --name ddm-run --network ddm-net -v ddm-vol:/d -p 18080:80 -e SECRETENV=x alpine:3.20 sleep 600`. Chaque sortie
est sur **stderr**, stdout est vide.

| Commande | Docker 29.10.1 (28.5.2 identique) | exit | Podman 6.2.1 et 5.8.11 (rootful et rootless identiques) | exit |
|---|---|---|---|---|
| `$E rm ddm-run` | `Error response from daemon: cannot remove container "ddm-run": container is running: stop the container before removing or force remove` | 1 | `Error: cannot remove container <id> as it is running - running or paused containers cannot be removed without force: container state improper` | 2 |
| `$E rmi alpine:3.20` | `Error response from daemon: conflict: unable to remove repository reference "alpine:3.20" (must force) - container <id12> is using its referenced image <id12>` | 1 | `Error: image used by <id>: image is in use by a container: consider listing external containers and force-removing image` | 2 |
| `$E network rm ddm-net` | `Error response from daemon: error while removing network: network ddm-net has active endpoints (name:"ddm-run" id:"<id12>")` puis une ligne `exit status 1` | 1 | `Error: "ddm-net" has associated containers with it. Use -f to forcibly delete containers and pods: network is being used` | 2 |
| `$E volume rm ddm-vol` | `Error response from daemon: remove ddm-vol: volume is in use - [<id>]` | 1 | `Error: volume ddm-vol is being used by the following container(s): <id>: volume is being used` | 2 |

Faits : le code de sortie du refus est **1 sous Docker et 2 sous Podman** pour ces quatre commandes. Le préfixe est
`Error response from daemon:` (Docker) ou `Error:` (Podman). Docker ajoute une ligne parasite `exit status 1` à la fin du
refus de `network rm`. Aucune différence entre N et N-1 pour ces quatre refus, ni entre rootful et rootless.

## 3. Refus pour nom déjà pris et pour port déjà pris

Commandes : `$E run -d --name ddm-run alpine:3.20 sleep 5` (nom pris) et
`$E run -d --name ddm-run2 -p 18080:80 alpine:3.20 sleep 5` (port 18080 déjà publié par `ddm-run`).

| Cas | Docker 29.10.1 et 28.5.2 | exit | Podman | exit |
|---|---|---|---|---|
| nom pris | `docker: Error response from daemon: Conflict. The container name "/ddm-run" is already in use by container "<id>". You have to remove (or rename) that container to be able to reuse that name.` suivi d'une ligne vide et de `Run 'docker run --help' for more information` | 125 | `Error: creating container storage: the container name "ddm-run" is already in use by <id>. You have to remove that container to be able to reuse that name: that name is already in use, or use --replace to instruct Podman to do so.` | 125 |
| port pris, rootful 6.2.1 | stdout : l'identifiant du conteneur (créé malgré l'échec) ; stderr : voir ci-contre | 125 | `Error: cannot bind tcp port :18080: address already in use` | 126 |
| port pris, rootful 5.8.11 | idem Docker | | `Error: cannot listen on the TCP port: listen tcp4 :18080: bind: address already in use` | 126 |
| port pris, rootless 6.2.1 et 5.8.11 | idem Docker | | `Error: pasta failed with exit code 1:` puis `Listen failed for HOST TCP port */18080: Address in use` puis `Couldn't listen on requested ports`, plus une ligne vide | 126 |

Docker, port pris (stderr, 29.10.1) : `docker: Error response from daemon: failed to set up container networking: driver failed programming external connectivity on endpoint ddm-run2 (<id>): Bind for 0.0.0.0:18080 failed: port is already allocated`, plus `Run 'docker run --help' for more information`.
Fait notable : **Docker crée le conteneur, affiche son identifiant sur stdout, puis échoue** (le conteneur reste `Created`) ; Podman n'affiche rien sur stdout. Le nom pris est reconnaissable aux mots `already in use` des deux côtés ; le port pris à
`port is already allocated` (Docker), `address already in use` (Podman rootful) ou `Address in use` (Podman rootless, pasta). Le code de sortie ne distingue pas les deux cas sous Docker (125 les deux), il les distingue sous Podman (125 / 126).

## 4. `volume prune`, avec et sans `-a`, et son rapport

Préparation : un volume nommé `ddm-v1` non utilisé et un volume anonyme non utilisé (`$E run --name ddm-vol-c -v /anon alpine:3.20 true`
puis `$E rm ddm-vol-c`). Commandes : `$E volume prune -f` puis (après avoir refait un anonyme) `$E volume prune -a -f`, puis la forme interactive `echo y | $E volume prune [-a]`.

| Commande | Docker 29.10.1 et 28.5.2 | Podman 6.2.1 | Podman 5.8.11 |
|---|---|---|---|
| `volume prune -f` | supprime **seulement l'anonyme** ; sortie `Deleted Volumes:`, une ligne par volume, ligne vide, `Total reclaimed space: 0B`; `ddm-v1` reste | supprime **seulement l'anonyme** ; sortie : une ligne par volume supprimé, **pas d'en-tête, pas de total** ; `ddm-v1` reste | supprime **tous les volumes inutilisés, nommés compris** (`ddm-v1` et l'anonyme) ; même sortie sans en-tête |
| `volume prune -a -f` | supprime aussi les nommés ; même rapport que ci-dessus (`Deleted Volumes:` ...) | supprime aussi les nommés ; une ligne par volume | **`Error: unknown shorthand flag: 'a' in -a` puis `See 'podman volume prune --help'`, exit 125** : le drapeau n'existe pas |
| `echo y \| volume prune` (interactif) | `WARNING! This will remove anonymous local volumes not used by at least one container.` puis `Are you sure you want to continue? [y/N] ` puis `Total reclaimed space: 0B` | `WARNING! This will remove anonymous local volumes not used by at least one container. The following volumes will be removed:` puis la liste (ou `No dangling anonymous volumes found`) | `WARNING! This will remove all volumes not used by at least one container. The following volumes will be removed:` puis la liste, la confirmation, la liste de nouveau |

Faits : le rapport de Docker est `Deleted Volumes:` + liste + `Total reclaimed space: <n>B` (le total est `0B` ici, les volumes étaient
vides). Celui de Podman est la **liste brute des noms, sans en-tête ni total**. **La portée de `volume prune` sans `-a` change entre Podman 5.8.11 (tout
volume inutilisé) et 6.2.1 (anonymes seulement, comme Docker)** : un `volume prune` lancé sur Podman N-1 supprime des volumes nommés. Rootless : mêmes résultats que rootful.

## 5. `inspect`, stdout et stderr séparés

Commandes : `$E inspect ddm-run`, `$E inspect nonexistent-ddm`, `$E inspect ddm-run nonexistent-ddm`, avec et sans
`--format '{{.State.Status}}'` ; les flux lus à part.

| Cas | Docker 29.10.1 | Docker 28.5.2 | Podman 6.2.1 et 5.8.11 |
|---|---|---|---|
| objet absent, stdout | `[]` (sans `--format`) ou ligne vide (avec) | idem | `[]` (sans `--format`) ou vide (avec) |
| objet absent, stderr | `error: no such object: nonexistent-ddm` | `Error: No such object: nonexistent-ddm` | `Error: no such object: "nonexistent-ddm"` (nom entre guillemets) |
| objet absent, exit | 1 | 1 | **125** |
| un présent et un absent | stdout : l'objet présent ; stderr : le message ci-dessus ; exit 1 | idem | stdout : l'objet présent ; stderr : le message ; exit **125** |

Faits : un objet absent n'est jamais sur stdout, et **un objet présent est quand même imprimé** quand un autre est absent (le
code de sortie est non nul). **La casse du message d'erreur de Docker change entre N-1 (`Error: No such object`) et N (`error: no such object`)** : une
recherche de sous-chaîne doit être insensible à la casse. Le JSON de Podman est indenté de cinq espaces (Docker : quatre) ;
`State.OciVersion` est `1.3.0` en 6.2.1 et `1.2.1` en 5.8.11.

## 6. Labels de projet Compose

Fichier : un service `web` (`alpine:3.20`, `sleep 600`), projet `-p ddmproj`. Lus par
`$E ps --filter label=com.docker.compose.project --format '{{.Names}}|{{.Labels}}'` et
`$E inspect --format '{{json .Config.Labels}}' <nom>`.

| | Docker (`docker compose` v5.8.0, N et N-1) | Podman (`podman compose` avec `podman-compose` 1.0.6, 6.2.1 et 5.8.11, rootful et rootless) |
|---|---|---|
| nom du conteneur | `ddmproj-web-1` | `ddmproj_web_1` |
| `com.docker.compose.project` | `ddmproj` | `ddmproj` |
| `com.docker.compose.service` | `web` | `web` |
| `com.docker.compose.container-number` | `1` | `1` |
| `com.docker.compose.project.working_dir` | chemin absolu | chemin absolu |
| `com.docker.compose.project.config_files` | chemin absolu | `compose.yaml` (relatif) |
| `com.docker.compose.config-hash`, `.oneoff`, `.depends_on`, `.image`, `.version` | présents (`.version` = `5.8.0`) | **absents** |
| familles propres | aucune | `io.podman.compose.project`, `.config-hash`, `.version` (`1.0.6`) et `PODMAN_SYSTEMD_UNIT=podman-compose@ddmproj.service` |

Fait : avec `podman-compose` 1.0.6, la clé `com.docker.compose.project` est posée, donc le filtre actuel la trouve ; la clé
`io.podman.compose.project` aussi. Le nom de conteneur suit un autre séparateur. Le réseau est créé avec les deux labels de projet
(`io.podman.compose.project`, `com.docker.compose.project`). Aucune différence entre N et N-1 de Podman, ni entre rootful et rootless.
**Non mesuré** : `podman compose` avec le fournisseur `docker-compose` (le binaire n'a pas été installé : voir H8).

## 7. Événements `exec` et `update` (H9, H10)

**Événements** : `$E events --format '{{json .}}'` (puis `$E events` sans format) lancés 6 s, pendant lesquels
`$E exec ddm-run echo CANARY_SECRET_123` est exécuté.

- Docker 29.10.1 : `"Action":"exec_create: echo CANARY_SECRET_123"` et `"Action":"exec_start: echo CANARY_SECRET_123"`, puis `"Action":"exec_die"`. Format par défaut :
  `container exec_start: echo CANARY_SECRET_123 <id> (execID=..., image=alpine:3.20, name=ddm-run)`. **Le canari est présent.**
- Docker 28.5.2 : pareil, avec en plus les champs hérités `"status"`, `"id"` et `"from"` dans le JSON (`"status":"exec_create: echo CANARY_SECRET_123"`). **Canari présent, y compris dans `status`.**
- Podman 6.2.1 et 5.8.11, rootful et rootless : `"Status":"exec"` (aucune commande), puis `"Status":"exec_died"` ; format par défaut `container exec <id> (image=..., name=ddm-run)`. **Le canari est absent.** `exec_died` porte `execID` en 6.2.1 (dans `Attributes`) et **ne le porte pas en 5.8.11** (`Attributes` vide). Les noms de champs JSON sont `Status`, `Name`, `Image`, `Attributes` (Docker : `Action`, `Actor.Attributes`).

**`update`** : `$E run -d --name ddm-run --memory 128m --memory-swap 256m alpine:3.20 sleep 600`, puis `$E update --memory 64m ddm-run`, `$E update --memory 512m ddm-run`, `$E update --memory 64m --memory-swap 128m ddm-run`, `$E update --cpus 0.5 ddm-run`.

| Commande | Docker 29.10.1 et 28.5.2 | Podman 6.2.1 et 5.8.11 (rootful et rootless) |
|---|---|---|
| `update --memory 64m` | accepté, stdout `ddm-run`, exit 0 | accepté, stdout l'identifiant complet, exit 0 |
| `update --memory 512m` (au-dessus du swap 256m posé) | **refusé**, exit 1 : `Error response from daemon: Cannot update container <id>: Memory limit should be smaller than already set memoryswap limit, update the memoryswap at the same time` | accepté, exit 0 |
| `update --memory 64m --memory-swap 128m` | accepté ; `HostConfig.Memory`/`MemorySwap` = `67108864 134217728` | accepté, mêmes valeurs |
| `update --cpus 0.5` | accepté | accepté |

## 8. Contradiction entre `network.md` et le commentaire de `engine.go` (H2)

Constat, sans correction (règle : une mesure qui contredit le code est gelée et notée ; la correction est une PR distincte) :

- `docs/architecture/network.md`, section « The container engine », deuxième puce : « No measurement has been taken against a real podman; `TestTheTwoTemplateSetsAreStillUnmeasured` fails the day the two sets stop matching ». Même ligne d'idée à la ligne 707 : le côté `podman` de `RepoDigests` « has not been measured against a real `podman` ».
- `internal/engine/engine.go`, commentaire de `podmanTemplates` : « diverges from dockerTemplates on the three outputs measured against a real `podman system service` (§3.67) » (`Info`, `NetworkLS`, `SystemDF`), et « the other nine outputs were checked against the same podman and matched ». Le commentaire de `dockerTemplates` dit en revanche que `podmanTemplates` « stays a copy until the measurement described on Templates has been made ».
- Le numéro **5.7.0** n'est **pas** dans `engine.go` : il est dans des commentaires de `internal/docker/registry.go` (« measured on 2026-09-25 (docker 29.7.2, podman 5.7.0) »), `internal/docker/exec.go` et `internal/docker/login_state_test.go`. Le commentaire de `engine.go` ne donne aucune version de Podman, ni date ni moteur rootless.
- `network.md` dit aussi (autour de la ligne 1261) « Measured on Docker and Podman », ce qui contredit son propre « No measurement has been taken ».

La contradiction est **constatée** : un texte affirme une mesure contre un vrai Podman (le code, avec 5.7.0 ailleurs), l'autre l'exclut. Ce relevé n'a pas mesuré les gabarits `--format` (hors périmètre OC-01), donc il ne tranche pas lequel des deux a raison sur ces gabarits. Il apporte seulement une mesure datée (Podman 6.2.1 et 5.8.11) de `ps`, `inspect`, `volume`, `events`, `update`.

## 9. Hypothèses du brief

| H | Énoncé | Verdict | Preuve |
|---|---|---|---|
| H1 | Les formats de statut (santé), de labels Compose, de stderr de refus et de rapport de prune diffèrent entre Docker et Podman et entre N et N-1. | **Confirmée** | Entre moteurs : `(health: starting)` contre `(starting)` (1), codes de refus 1 contre 2 (2), 125/126 pour le port (3), rapport de `volume prune` avec `Deleted Volumes:` et total contre liste brute (4), labels (6). | H2 | `network.md` et le commentaire de `engine.go` se contredisent sur la mesure Podman (5.7.0). | **Confirmée, avec une correction du libellé** | Voir 8 : la contradiction existe, mais le numéro 5.7.0 est dans `internal/docker/*`, pas dans `engine.go`. |

| H9 | `docker events` met la commande d'un `exec` dans l'action (`exec_start: …`), donc un secret possible ; le format JSON de Podman diffère. | **Confirmée pour Docker, infirmée pour Podman** | Docker 29.10.1 et 28.5.2 : `exec_create: echo CANARY_SECRET_123` et `exec_start: echo CANARY_SECRET_123` dans `Action` (et dans `status` en 28.5.2). | H10 | `update` n'existe pas dans toutes les versions N / N-1 de Podman ; abaisser la mémoire sous la limite de swap est refusé par Docker. | **Première partie infirmée, seconde partie à reformuler** | `podman update` existe et fonctionne en 6.2.1 et 5.8.11, rootful et rootless (7) ; sa disponibilité avant 5.8 n'est pas mesurée. Docker 29.10.1 et 28.5.2 refuse non pas d'abaisser la mémoire (`--memory 64m` est accepté) mais de **relever** `--memory` au-dessus du swap déjà posé (`Memory limit should be smaller than already set memoryswap limit`) ; Podman l'accepte. |

## Limites

- Une seule image (`alpine:3.20`) ; pas de pull, pas de `stats`, pas de réseau hors du pont par défaut.
- Podman : build statique tiers ; la santé automatique ne s'y est pas déclenchée (1), à confirmer avec un paquet de distribution.
- Docker N et N-1 utilisent le même plugin Compose v5.8.0 : les labels de Compose ne mesurent donc pas une différence N/N-1 de Docker.
- Une seule exécution par configuration : les durées (`Up 5 seconds`) varient, pas les formats.
